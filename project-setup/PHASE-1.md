# Phase 1 - Architecture & Standards

Read by `/project-setup` when Phase 1 work is needed.

## Existing docs convergence

When running /project-setup on a codebase that already has documentation not generated by this skill family (e.g., a hand-written README, an existing CLAUDE.md, scattered convention notes, test guidelines in a wiki or contributing guide), converge before generating.

Check for pre-existing docs that overlap with what Phase 1 produces:
- **CONVENTIONS.md or equivalent** (CONTRIBUTING.md, style guide, linter config with documented rules)
- **TESTING.md or equivalent** (test strategy doc, CI config with documented expectations)
- **CLAUDE.md or AGENTS.md** (existing agent instructions)
- **docs/adr/ or similar decision records**

If found: read them, extract what's still valid, and fold it into the generated output.
Don't ask the user to re-decide things the existing docs already answer.
Don't overwrite without acknowledging what was there.

```
Found existing docs that overlap with what I'll generate:
  - CONTRIBUTING.md has naming conventions (lines 12-45)
  - .github/TESTING.md has test expectations
  - CLAUDE.md exists with project structure

I'll fold the relevant content into the skill family's format.
Anything to preserve as-is, or should I consolidate freely?
```

Skip this section entirely when running on a fresh project or when all existing docs were generated by prior /project-setup runs.

## Architecture decisions

Invoke `/grill-with-docs` for each decision that meets the ADR threshold (hard to reverse, surprising without context, real trade-off). For obvious stack choices that don't warrant an ADR, document them in ARCHITECTURE.md directly.

Assemble 6-8 relevant architecture areas from the catalog in [REFERENCES.md](REFERENCES.md#architecture-decision-catalog) based on Phase 0 context. Mark 4 as Recommended using the project-type mapping in the catalog.

Present via AskUserQuestion (multiSelect: true):

**"Which architecture areas need decisions?"** (select all that apply)

Adapt descriptions to the project profile per the catalog's adaptation rules. Unselected areas can be deferred to Phase 3 (surfaced by /check-in as pre-build checkpoint items) or skipped entirely.

## Naming conventions

Generate a `CONVENTIONS.md` at the repo root by interrogating the implementer about their stack's conventions. Ask about:
- Function naming patterns (API calls, event handlers, boolean returns)
- Component/class naming patterns
- Type/interface naming patterns
- File naming patterns
- For migrations: which legacy patterns to mirror vs. deliberately break from

Keep it short - one line per convention. This file grows during Phase 3 (vertical slice or MVP build) when real patterns emerge from actual code.

Do NOT prescribe framework-specific conventions. Ask what the project uses, then document the answers.

Add one line to the generated CLAUDE.md: `When writing new code or reviewing naming patterns, read CONVENTIONS.md.`

## UI pattern library (if applicable)

For projects with a UI layer, enumerate the recurring patterns the project will use. Each pattern gets:
- A name
- A brief contract (what data it expects, what it renders/does)
- Which architecture decisions it depends on

These patterns are validated in Phase 3 (vertical slice) by the implementation verb.

## Testing template

Before generating TESTING.md, ask via AskUserQuestion:

**"What's your testing approach?"**
- **Integration-first (Recommended)** - test user workflows end-to-end, unit test complex logic only
- **TDD** - test-first for all features, high unit coverage
- **Structural enforcement** - automated convention checks, smoke tests, minimal unit tests

Store as `testing-philosophy: integration-first | tdd | structural-enforcement` in SCOPE.md frontmatter. This sets the default stance - Phase 3 refines from real patterns, /project-setup resume path allows revisiting.

Generate a `TESTING.md` at the repo root. Seed with test expectations by complexity tier, emphasizing the chosen philosophy. One example per pattern type:

- **Smoke test** - does it render without crashing?
- **Structural enforcement** - do conventions hold across the codebase?
- **Characterization / golden master** (migration) - does the new system match the old?
- **Integration workflow** - does a multi-step user flow work end-to-end?

Keep it short. This file is refined during Phase 3 (vertical slice or MVP build) when real test patterns emerge from actual code.

Add one line to the generated CLAUDE.md: `When writing tests, read TESTING.md for patterns and expectations.`

## Documentation structure

Create this tree (adapt to the project):

```
docs/
  SCOPE.md
  DEPENDENCIES.md
  ARCHITECTURE.md
  adr/                        # ADRs via /grill-with-docs
  design/                     # Design system docs (created during 6b-i)
  reference/
    features/
      _TEMPLATE.md            # Feature spec template
    logic/
      _TEMPLATE.md            # Logic doc template
  specs/                      # Feature specs via /spec
  improvements/               # UX improvement ideas (capture, don't implement)
  local/                      # Gitignored - see LOCAL-DOCS-REFERENCE.md for full structure
```

The `docs/local/` structure scales with the project intake profile.
See [LOCAL-DOCS-REFERENCE.md](LOCAL-DOCS-REFERENCE.md) for the canonical file list, formats, scaling rules, and which skills own each file.

## Spec templates

Generate two templates grilled to the project's needs.

**docs/reference/features/_TEMPLATE.md** - adapt sections based on stack:
- Overview (one paragraph: what this screen does)
- Fields & Controls (table: field, type, source, editable, default)
- Interaction Behaviors (table: control, behavior, notes - e.g., sortable, resizable, filterable)
- Conditional Visibility (what shows/hides based on state)
- Toolbar/Navigation Actions (buttons, links, what they do)
- Navigation (how user gets here, where they can go)
- Validation Rules
- Change Log

**docs/reference/logic/_TEMPLATE.md**:
- Data Model (fields, types, nullability)
- Relationships (to other entities)
- Status Lifecycle (state machine if applicable)
- Business Rules
- Calculated Fields
- Edge Cases
- Known Bugs / Quirks
- Change Log

## Documentation Map

After generating the documentation structure above, write the Documentation Map to CLAUDE.md.
The map tells every skill where project files live - skills resolve references through it, never hardcoded paths.

Generate the map based on the selected tier (see [SCOPE-REFERENCE.md](SCOPE-REFERENCE.md) for tier details):

```markdown
## Documentation Map

| Concept | Path | Status |
|---------|------|--------|
| Domain glossary | CONTEXT.md | Active |
| Naming conventions | CONVENTIONS.md | Active |
| Test expectations | TESTING.md | Active |
| Scope boundaries | SCOPE.md | Active |
| Architecture decisions | docs/adr/ | Active |
| Architecture overview | ARCHITECTURE.md | Active |
| Skill state | .claude/ | Active |
```

Small tier: only SCOPE.md and Skill state rows.
Large tier: conventions/ subpaths replace CONVENTIONS.md and TESTING.md rows.
Mark rows as "Planned" if the file will be created later (e.g., ARCHITECTURE.md during Phase 1 architecture decisions).

On re-entry, read the existing map and only update entries that changed.

## CLAUDE.md generation

Generate the project's CLAUDE.md with these sections (each concise):

### Repository Overview
One paragraph: what this project is.

### Development
Commands to install, run, build, test.

### Project Structure
Directory tree with one-line descriptions.

### Branch Workflow
Document the tier structure. Example:
- `main` - production, protected
- `preview` - staging/QA
- `beta` - integration testing
- Feature branches off `beta`, merged back via PR

### Design Exploration Policy (design-system archetype only)
Skip this section and Design Archival if no design-system archetype is selected.

Isolated design experimentation is allowed on separate branches (worktree or design branch) that do not tie into production components. Guardrails:
- Time-boxed: set a limit before starting, stop when it hits
- Critically questioned: is this for user benefit and grounded in domain truth, or just modern UX cloning that doesn't respect the domain?
- Captured: if the experiment validates, write it up in `docs/improvements/` before integrating
- Periodically merge parent branch to keep docs and domain knowledge current on the design branch

### Design Archival
Before each new design direction, tag the current state:
```
git tag design/{nn}-{slug}
```
After tagging, add a journal entry in `docs/local/design-journal.md`:
```
## {date} - {what you explored}
### design/{nn}-{slug}
{One sentence: what this variant does differently}
{One sentence: why it was chosen or rejected}
Screenshot: {path or inline}
```
Tags are diff-able (`git diff design/01..design/02`), restorable (`git checkout design/01`), and survive indefinitely. The journal tracks reasoning; tags preserve the running code.

### Agent Coordination
- Task brief template: What, Files claimed, Inputs, Output, Model (Sonnet for mechanical / Opus for judgment), Constraints
- When to use workflows vs parallel agents vs inline subagents
- Concurrent agent protocol (ACTIVE-WORK tracker, file claiming, stale entry policy) - wired by the "Concurrent agent coordination" step below

### Change Protocol
1. When a dependency changes: update spec first, then code. Never code without updating spec.
2. When scope changes: update SCOPE.md, update inventory, ADR if significant.
3. When updating a spec: add entry to the Change Log section at bottom (date + one-liner).

### Enforcement
Identify which rules need hooks (deterministic enforcement) vs CLAUDE.md (advisory):
- Hooks: branch protection, test-before-push, forbidden file patterns
- Advisory: template compliance, brief format, documentation currency

Generate project-specific hooks where identified.

### Concurrent agent coordination (strongly recommended)

After CLAUDE.md is generated, ask via `AskUserQuestion` (multiSelect: true):

**Which hooks do you want to set up?**
- **ACTIVE-WORK tracker (Recommended)** - UserPromptSubmit hook that injects concurrent agent tracker into every prompt. Prevents file conflicts when multiple sessions modify the codebase simultaneously.
- **I have other hooks I want to set up** - Describe additional hooks to wire. Each gets added to `.claude/settings.json` and templated in [REFERENCES.md](REFERENCES.md#hook-catalog) for future projects.

If ACTIVE-WORK is selected, follow the "Concurrent Agent Coordination" template in [REFERENCES.md](REFERENCES.md#hook-catalog).
If other hooks is selected, grill the user on each additional hook: what event triggers it, what it checks or injects, and what the failure mode looks like. Add each to the Hook Catalog in REFERENCES.md.
