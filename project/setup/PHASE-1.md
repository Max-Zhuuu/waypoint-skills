# Phase 1 - Architecture & Standards

Read by `/setup` when Phase 1 work is needed.

## Existing docs convergence

When running /setup on a codebase that already has documentation not generated by this skill family (e.g., a hand-written README, an existing CLAUDE.md, scattered convention notes, test guidelines in a wiki or contributing guide), converge before generating.

Check for pre-existing docs that overlap with what Phase 1 produces:
- **CONVENTIONS.md or equivalent** (CONTRIBUTING.md, style guide, linter config with documented rules)
- **TESTING.md or equivalent** (test strategy doc, CI config with documented expectations)
- **CLAUDE.md or AGENTS.md** (existing agent instructions)
- **docs/adr/ or similar decision records**

If found: read them, extract what's still valid, and fold it into the generated output.
Don't ask the user to re-decide things the existing docs already answer.
Don't overwrite without acknowledging what was there.

```
Found existing docs that overlap with what I'll generate:
  - CONTRIBUTING.md has naming conventions (lines 12-45)
  - .github/TESTING.md has test expectations
  - CLAUDE.md exists with project structure

I'll fold the relevant content into the skill family's format.
Anything to preserve as-is, or should I consolidate freely?
```

Skip this section entirely when running on a fresh project or when all existing docs were generated by prior /setup runs.

## Architecture decisions

Invoke `/grill-with-docs` for each decision that meets the ADR threshold (hard to reverse, surprising without context, real trade-off). For obvious stack choices that don't warrant an ADR, document them in ARCHITECTURE.md directly.

Assemble 6-8 relevant architecture areas from the catalog in [REFERENCES.md](REFERENCES.md#architecture-decision-catalog) based on Phase 0 context. Mark 4 as Recommended using the project-type mapping in the catalog.

Present via AskUserQuestion (multiSelect: true):

**"Which architecture areas need decisions?"** (select all that apply)

Adapt descriptions to the project profile per the catalog's adaptation rules. Unselected areas can be deferred to Phase 3 (surfaced by /check-in as pre-build checkpoint items) or skipped entirely.

## Naming conventions

Read [../../templates/CONVENTIONS.md](../../templates/CONVENTIONS.md) and populate it by interrogating the implementer about their stack's conventions. Ask about:
- Function naming patterns (API calls, event handlers, boolean returns)
- Component/class naming patterns
- Type/interface naming patterns
- File naming patterns
- For migrations: which legacy patterns to mirror vs. deliberately break from

Keep it short - one line per convention. This file grows during Phase 3 (vertical slice or MVP build) when real patterns emerge from actual code.

Do NOT prescribe framework-specific conventions. Ask what the project uses, then document the answers.

Add one line to the generated CLAUDE.md: `When writing new code or reviewing naming patterns, read CONVENTIONS.md.`

## Testing template

Before generating TESTING.md, ask via AskUserQuestion:

**"What's your testing approach?"**
- **Integration-first (Recommended)** - test user workflows end-to-end, unit test complex logic only
- **TDD** - test-first for all features, high unit coverage
- **Structural enforcement** - automated convention checks, smoke tests, minimal unit tests

Store as `testing-philosophy: integration-first | tdd | structural-enforcement` in SCOPE.md frontmatter. This sets the default stance - Phase 3 refines from real patterns, /setup resume path allows revisiting.

Read [../../templates/TESTING.md](../../templates/TESTING.md) and populate it, emphasizing the chosen philosophy. Keep it short. This file is refined during Phase 3 (vertical slice or MVP build) when real test patterns emerge from actual code.

Add one line to the generated CLAUDE.md: `When writing tests, read TESTING.md for patterns and expectations.`

## Documentation structure

Create the three-tier documentation structure (adapt to the project):

```
docs/
  GLOSSARY.md                    # Domain glossary
  program/                       # What the system IS
    ARCHITECTURE.md              # Stack, state management, data flow, deps
    TESTING.md                   # Test expectations by tier
    conventions/
      NAMING.md                  # Variables, functions, components, files
      UX.md                      # Interaction patterns, confirmations
    adr/                         # ADRs via /grill-with-docs
    features/                    # Target system feature docs
  implementation/                # What we're DOING
    SCOPE.md                     # In/out/uncertain
    CONCERNS.md                  # Questions, assumptions, issues, milestones
    specs/                       # Feature specs via /spec
      resolved/                  # Archived specs by date (YYYY-MM/)
    handoffs/                    # Cross-team requests
    improvements/                # UX improvement ideas (capture, don't implement)
    archive/                     # Superseded docs
  local/                         # Gitignored working state
    learnings/
    notes/
```

For migration projects, add `docs/program-legacy-{source}/` alongside `program/`:
```
  program-legacy-{source}/       # Source system reference
    features/
      _TEMPLATE.md               # Feature spec template
    logic/
      _TEMPLATE.md               # Logic doc template
```

The `docs/local/` structure is minimal: `learnings/` and `notes/`.
See [LOCAL-DOCS-REFERENCE.md](LOCAL-DOCS-REFERENCE.md) for scaling rules and which skills own each file.

## Documentation Map

After generating the documentation structure above, write the Documentation Map to CLAUDE.md.

```markdown

  **GLOSSARY.md**                # Domain glossary - canonical terms, avoid-lists
  program/                       # What the system IS
    **ARCHITECTURE.md**          # Stack, state management, data flow, deps

    conventions/
      **NAMING.md**              # Variables, functions, components
      UX.md                      # Interaction patterns, confirmations
    adr/                         # Architecture decision records
  implementation/                # What we're DOING
    **SCOPE.md**                 # In/out/uncertain
    **CONCERNS.md**              # Questions, assumptions, issues, milestones
    specs/                       # Feature specs (flat, active)

```

Small tier: flatten (SCOPE.md at root, skip program/ directory).
Large tier: add program/STRUCTURE.md, program/DESIGN.md, program/features/, implementation/handoffs/.
Migration tier: add program-legacy-{source}/ with features/, logic/, TEMPLATES/.

On re-entry, read the existing map and only update entries that changed.
As scope scales, nudge the user to add entries for new doc areas.

## CLAUDE.md generation

Read [../../templates/CLAUDE.md](../../templates/CLAUDE.md) and populate it from Phase 0 and Phase 1 answers.

The template includes: Repository Overview, Development commands, Project Structure, Project Scaffold, Documentation Map, Branch Workflow, Agent Coordination, and Change Protocol.

Add these sections only when applicable:

### Design Exploration Policy (design-system archetype only)
Skip this section and Design Archival if no design-system archetype is selected.

Isolated design experimentation is allowed on separate branches (worktree or design branch) that do not tie into production components. Guardrails:
- Time-boxed: set a limit before starting, stop when it hits
- Critically questioned: is this for user benefit and grounded in domain truth, or just modern UX cloning that doesn't respect the domain?
- Captured: if the experiment validates, write it up in `docs/improvements/` before integrating
- Periodically merge parent branch to keep docs and domain knowledge current on the design branch

### Design Archival
Before each new design direction, tag the current state:
```
git tag design/{nn}-{slug}
```
After tagging, add a journal entry in `docs/local/design-journal.md`.
Tags are diff-able, restorable, and survive indefinitely. The journal tracks reasoning; tags preserve the running code.

### Enforcement
Identify which rules need hooks (deterministic enforcement) vs CLAUDE.md (advisory):
- Hooks: branch protection, test-before-push, forbidden file patterns
- Advisory: template compliance, brief format, documentation currency

Generate project-specific hooks where identified.

### Concurrent agent coordination (strongly recommended)

After CLAUDE.md is generated, ask via `AskUserQuestion` (multiSelect: true):

**Which hooks do you want to set up?**
- **CONCERNS.md Claims (Recommended)** - UserPromptSubmit hook that injects concurrent agent tracker into every prompt. Prevents file conflicts when multiple sessions modify the codebase simultaneously.
- **I have other hooks I want to set up** - Describe additional hooks to wire. Each gets added to `.claude/settings.json` and templated in [REFERENCES.md](REFERENCES.md#hook-catalog) for future projects.

If Claims hook is selected, follow the "Concurrent Agent Coordination" template in [REFERENCES.md](REFERENCES.md#hook-catalog).
If other hooks is selected, grill the user on each additional hook: what event triggers it, what it checks or injects, and what the failure mode looks like. Add each to the Hook Catalog in REFERENCES.md.
