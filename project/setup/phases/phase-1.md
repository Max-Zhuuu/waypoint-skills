# Phase 1 - Architecture & Standards

Read by `/setup` when Phase 1 work is needed.

## Existing docs convergence

When running /setup on a codebase that already has documentation not generated by this skill family (e.g., a hand-written README, an existing CLAUDE.md, scattered convention notes, test guidelines in a wiki or contributing guide), converge before generating.

Check for pre-existing docs that overlap with what Phase 1 produces:
- **CONVENTIONS.md or equivalent** (CONTRIBUTING.md, style guide, linter config with documented rules)
- **TESTING.md or equivalent** (test strategy doc, CI config with documented expectations)
- **CLAUDE.md or AGENTS.md** (existing agent instructions)
- **docs/adr/ or similar decision records**
- **architecture-rule-catalogue.md** (rule families, severity tiers, execution tiers)
- **contracts/*-endpoints.json** (endpoint registries)

If found: read them, extract what's still valid, and fold it into the generated output.
Don't ask the user to re-decide things the existing docs already answer.
Don't overwrite without acknowledging what was there.

```
Found existing docs that overlap with what I'll generate:
  - CONTRIBUTING.md has naming conventions (lines 12-45)
  - .github/TESTING.md has test expectations
  - CLAUDE.md exists with project structure

I'll fold the relevant content into the skill family's format.
Anything to preserve as-is, or should I consolidate freely?
```

Skip this section entirely when running on a fresh project or when all existing docs were generated by prior /setup runs.

## Architecture decisions

Three paths based on what exists.

### Path A - Architecture rule catalogue exists

When the project has an `architecture-rule-catalogue.md` (or similar governance document with rule families, severity tiers, execution tiers):

1. Read the catalogue. Parse rule families, severity distribution (BLOCK/RATCHET/WARN), execution tiers (T0-T3), and any open items section.
2. For each rule family, initialize a grill checklist item: family ID, name, rule count, open items.
3. Invoke `/grill-with-docs` to grill each family systematically - one family at a time, depth-first. Follow the methodology in [catalogue-grill.md](../../task/grill-with-docs/reference/catalogue-grill.md).
4. Cross-reference against existing ADRs. Identify families with no ADR coverage - these are grill priorities.
5. Open items in the catalogue are high-priority grill targets. For each: what are the options, what blocks the decision, what's the recommended position.
6. Produce consolidated decision-tree ADRs: each answers a root question with branching sub-decisions. Target 6-8 ADRs for a complex project.
7. For API-consuming projects: check for endpoint registries (`contracts/*-endpoints.json`). If absent, offer to scaffold one from `../../templates/endpoint-registry.json`.

### Path B - No catalogue, moderate/large project

When no rule catalogue exists but the project tier is moderate or large:

1. Offer to bootstrap: "This project's complexity warrants an architecture rule catalogue. Want me to create one?"
2. If accepted: start with severity definitions (BLOCK = correctness/security, RATCHET = coverage metrics, WARN = convention drift) and execution tiers (T0 <2s on save, T1 <20s pre-commit, T2 <8min CI, T3 unbounded nightly).
3. Seed rule families from the grill, not from a template. Ask: "What rule families does this project need?" Common starters: Style, File placement, Contracts/schemas, Testing coverage, Config/hardcoded strings, Auth/security.
4. Mark all initial rules as WARN. Let the team ratchet up severity as conventions mature.
5. Follow the bootstrapping section in [catalogue-grill.md](../../task/grill-with-docs/reference/catalogue-grill.md).
6. Then proceed as Path A with the new catalogue.

### Path C - Small project, no catalogue

Fall back to the existing area catalog.

Assemble 6-8 relevant architecture areas from the catalog in [references.md](../reference/references.md#architecture-decision-catalog) based on Phase 0 context. Mark 4 as Recommended using the project-type mapping in the catalog.

Present via AskUserQuestion (multiSelect: true):

**"Which architecture areas need decisions?"** (select all that apply)

Adapt descriptions to the project profile per the catalog's adaptation rules. Unselected areas can be deferred to Phase 3 (surfaced by /check-in as pre-build checkpoint items) or skipped entirely.

### All paths

Invoke `/grill-with-docs` for each decision that meets the ADR threshold (hard to reverse, surprising without context, real trade-off). For obvious stack choices that don't warrant an ADR, document them in ARCHITECTURE.md directly.

## Naming conventions

Read [conventions-naming.md](../../../templates/conventions-naming.md) and [conventions-ux.md](../../../templates/conventions-ux.md), then populate them by interrogating the implementer about their stack's conventions. Ask about:
- Function naming patterns (API calls, event handlers, boolean returns)
- Component/class naming patterns
- Type/interface naming patterns
- File naming patterns
- For migrations: which legacy patterns to mirror vs. deliberately break from

Keep it short - one line per convention. This file grows during Phase 3 (vertical slice or MVP build) when real patterns emerge from actual code.

Do NOT prescribe framework-specific conventions. Ask what the project uses, then document the answers.

Add one line to the generated CLAUDE.md: `When writing new code or reviewing naming patterns, read CONVENTIONS.md.`

## UI pattern library (if applicable)

- Which architecture decisions it depends on

These patterns are validated in Phase 3 (vertical slice) by the implementation verb.

## Testing template

Before generating TESTING.md, ask via AskUserQuestion:

**"What's your testing approach?"**
- **Integration-first (Recommended)** - test user workflows end-to-end, unit test complex logic only
- **TDD** - test-first for all features, high unit coverage
- **Structural enforcement** - automated convention checks, smoke tests, minimal unit tests

Store as `testing-philosophy: integration-first | tdd | structural-enforcement` in SCOPE.md frontmatter. This sets the default stance - Phase 3 refines from real patterns, /setup resume path allows revisiting.

Read [../../../templates/TESTING.md](../../../templates/TESTING.md) and populate it, emphasizing the chosen philosophy. Keep it short. This file is refined during Phase 3 (vertical slice or MVP build) when real test patterns emerge from actual code.

Add one line to the generated CLAUDE.md: `When writing tests, read TESTING.md for patterns and expectations.`

## Convention enforcement scaffolding

Offer to create an initial suite of convention-enforcement tests. These are tests that verify conventions are followed, not feature tests. Read [convention-enforcement.md](../../process/convention-enforcement.md) for the full methodology.

Present via AskUserQuestion (multiSelect: true):

**"Which convention tests should I scaffold?"**
- **Structure tests (Recommended)** - verify file placement matches the project's canonical taxonomy
- **Import tests** - no cross-domain imports outside barrel files, no circular dependencies
- **Auth coverage tests** - every registered route has authentication enforcement
- **None for now** - skip, add later via `/tdd` Phase 4

Register scaffolded tests at the appropriate execution tier:
- Structure and import tests: T1 (pre-commit, <20s)
- Auth coverage: T2 (CI on PR, <8min)

## Hook scaffolding

Offer to configure `.claude/settings.json` with enforcement hooks. Read the hook-based enforcement section in [convention-enforcement.md](../../process/convention-enforcement.md).

Present via AskUserQuestion (multiSelect: true):

**"Which hooks do you want to set up?"**
- **Safety deny lists (Recommended)** - block destructive git operations (`git rebase`, `git push --force`) and cloud CLI (`az`, `aws`, `gcloud`) in `.claude/settings.local.json`
- **CONCERNS.md injection** - UserPromptSubmit hook that loads unresolved concerns into every prompt
- **Doc-sync reminders** - PostToolUse hooks that remind when related docs need updating after file edits
- **Concurrent agent coordination** - Claims tracker for multi-session work. Follow the template in [references.md](../reference/references.md#hook-catalog).

If additional hooks are described, grill the user on each: trigger event, what it checks, failure mode. Add to `.claude/settings.json`.

## Documentation structure

Create the three-tier documentation structure (adapt to the project):

```
docs/
  _GLOSSARY.md                   # Domain glossary (underscore sorts to top)
  program/                       # What the system IS
    ARCHITECTURE.md              # Stack, state management, data flow, deps
    TESTING.md                   # Test expectations by tier
    conventions/
      NAMING.md                  # Variables, functions, components, files
      UX.md                      # Interaction patterns, confirmations
    adr/                         # ADRs via /grill-with-docs
    features/                    # Target system feature docs
  implementation/                # What we're DOING
    SCOPE.md                     # In/out/uncertain
    CONCERNS.md                  # Questions, assumptions, issues, milestones
    specs/                       # Feature specs via /spec
      resolved/                  # Archived specs by date (YYYY-MM/)
    handoffs/                    # Cross-team requests
    improvements/                # UX improvement ideas (capture, don't implement)
    archive/                     # Superseded docs
  _local/                        # Gitignored working state (underscore sorts to top)
    learnings/
    notes/
```

For migration projects, add `docs/program-legacy-{source}/` alongside `program/`:
```
  program-legacy-{source}/       # Source system reference
    features/
      _TEMPLATE.md               # Feature spec template
    logic/
      _TEMPLATE.md               # Logic doc template
```

The `docs/_local/` structure is minimal: `learnings/` and `notes/`.
See [local-docs.md](../reference/local-docs.md) for scaling rules and which skills own each file.

## Deployment doc

If the project has any delivery target beyond a local checkout (a remote, a pipeline, a hosting destination), scaffold `DEPLOY.md` at the repo root.
Copy from [../../../templates/DEPLOY.md](../../../templates/DEPLOY.md) and populate the `waypoint:deploy` fenced block from Phase 0 dependency answers (hosting, CI/CD, environments): pick the adapter, name the tiers and their promote mode, and set the `load-bearing` globs to this project's dangerous surfaces.
`DEPLOY.md` is the sibling of ARCHITECTURE.md: architecture says how the system is built, deploy says how a change reaches production.
`/ship` reads it; without it, `/ship` fails loud.
For a purely local project with no delivery target, skip it - `/ship` treats a missing DEPLOY.md as a fail-loud stop (not as `adapter: local`, and never as vacuously safe).
Add a `DEPLOY.md` entry to the Documentation Map so skills resolve it through the map.

## Documentation Map

After generating the documentation structure above, write the Documentation Map to CLAUDE.md.
Tree format with bold markers (**) for key docs. Skills resolve through this map, never hardcoded paths.

```markdown
## Documentation Map

docs/
  **_GLOSSARY.md**               # Domain glossary - canonical terms, avoid-lists
  program/                       # What the system IS
    **ARCHITECTURE.md**          # Stack, state management, data flow, deps
    **TESTING.md**               # Test expectations by complexity tier
    conventions/
      **NAMING.md**              # Variables, functions, components
      UX.md                      # Interaction patterns, confirmations
    adr/                         # Architecture decision records
  implementation/                # What we're DOING
    **SCOPE.md**                 # In/out/uncertain
    **CONCERNS.md**              # Questions, assumptions, issues, milestones
    specs/                       # Feature specs (flat, active)
  _local/                        # Gitignored working state
```

Small tier: flatten (SCOPE.md at root, skip program/ directory).
Large tier: add program/STRUCTURE.md, program/DESIGN.md, program/features/, implementation/handoffs/.
Migration tier: add program-legacy-{source}/ with features/, logic/, TEMPLATES/.

On re-entry, read the existing map and only update entries that changed.
As scope scales, nudge the user to add entries for new doc areas.

## CLAUDE.md generation

Read [../../../templates/CLAUDE.md](../../../templates/CLAUDE.md) and populate it from Phase 0 and Phase 1 answers.

The template includes: Repository Overview, Development commands, Project Structure, Project Scaffold, Documentation Map, Branch Workflow, Agent Coordination, and Change Protocol.

Add these sections only when applicable:

### Design Exploration Policy (design-system archetype only)
Skip this section and Design Archival if no design-system archetype is selected.

Isolated design experimentation is allowed on separate branches (worktree or design branch) that do not tie into production components. Guardrails:
- Time-boxed: set a limit before starting, stop when it hits
- Critically questioned: is this for user benefit and grounded in domain truth, or just modern UX cloning that doesn't respect the domain?
- Captured: if the experiment validates, write it up in `docs/improvements/` before integrating
- Periodically merge parent branch to keep docs and domain knowledge current on the design branch

### Design Archival
Before each new design direction, tag the current state:
```
git tag design/{nn}-{slug}
```
After tagging, add a journal entry in `docs/_local/design-journal.md`.
Tags are diff-able, restorable, and survive indefinitely. The journal tracks reasoning; tags preserve the running code.

### Enforcement
Identify which rules need hooks (deterministic enforcement) vs CLAUDE.md (advisory):
- Hooks: branch protection, test-before-push, forbidden file patterns, safety deny lists
- Advisory: template compliance, brief format, documentation currency

Generate project-specific hooks where identified. If convention-enforcement tests were scaffolded above, add their execution tier to the appropriate hook or CI step.
