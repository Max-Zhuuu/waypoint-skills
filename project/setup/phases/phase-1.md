# Phase 1 - Architecture & Standards

Read by `/setup` when Phase 1 work is needed.

## Template selection

Before generating any content, detect project shape and offer the appropriate template.

### Lean template

Triggers when ALL of: no frontend, no design tokens, no multitenancy, single deployment target.
Typical for: stateless APIs, CLIs, libraries.

Lean CLAUDE.md structure:
```
# CLAUDE.md

<one-line project description>

## Commands
## Agent constraints
## Architecture
  ### Key design decisions
  ### Source layout
  ### Endpoints / API surface
  ### Error handling
  ### Testing
  ### Related repos
```

### Full template

Triggers when ANY of: has frontend, has design tokens, has multitenancy, multiple deploy targets.
Typical for: web apps, portal projects, migration projects.

Full CLAUDE.md structure:
```
# CLAUDE.md

<one-line project description>

## Commands
## Agent constraints
## Scope
  ### In / Out / Uncertain
  ### Constraints
  ### Resources
## Architecture
  ### Key design decisions
  ### Source layout
  ### Components and boundaries
  ### Data flow
## Conventions
## Deployment
## Product context
  ### Personas
  ### External connectors
## Auth pattern
## Testing
## References
```

Ask via AskUserQuestion when detection is ambiguous:
**"This project looks like a {detected shape}. Should I use the lean template (single Architecture section) or the full template (Scope, Conventions, Deployment, Product context sections)?"**
- **Lean (Recommended)** - if the project is a stateless API, CLI, or library
- **Full** - if the project has frontend, design tokens, multitenancy, or multiple deploy targets

## Existing docs convergence

When running /setup on a codebase that already has documentation not generated by this skill family (e.g., a hand-written README, an existing CLAUDE.md, scattered convention notes), converge before generating.

Check for pre-existing docs that overlap with what Phase 1 produces:
- **CLAUDE.md or AGENTS.md** (existing agent instructions)
- **docs/adr/ or similar decision records**
- **architecture-rule-catalogue.md** (rule families, severity tiers, execution tiers)
- **contracts/*-endpoints.json** (endpoint registries)
- **Legacy separate files** (SCOPE.md, CONVENTIONS.md, ARCHITECTURE.md, TESTING.md, DEPLOY.md, or their .json equivalents)

If legacy separate files found: offer to consolidate them into CLAUDE.md sections.
```
Found legacy project docs that should be consolidated into CLAUDE.md:
  - SCOPE.md (87 lines)
  - CONTEXT.md (149 lines)
  - DEPLOY.md (49 lines)

I'll fold the relevant content into CLAUDE.md sections and delete the originals.
Anything to preserve as-is, or should I consolidate freely?
```

If a CLAUDE.md already exists with the target section structure: activate the resume path instead (see resume-path.md).

## CLAUDE.md generation

All project documentation goes into CLAUDE.md as sections.
No separate SCOPE.md, CONVENTIONS.md, ARCHITECTURE.md, TESTING.md, or DEPLOY.md files.

### One-liner opener

Write a single sentence describing what this project is.
Model on marsoft-engine's style: direct, factual, no marketing language.

### ## Commands section

Place near the top of CLAUDE.md, right after the one-liner.
List the 5-6 commands an agent needs on day 1:

```markdown
## Commands

\`\`\`bash
<dev server command>      # Start local dev server
<test command>            # Run tests
<lint command>            # Lint
<build command>           # Build for production
<deploy command>          # Deploy (if applicable)
\`\`\`
```

Discover commands from package.json scripts, Makefile, pyproject.toml, or by asking the user.

### ## Agent constraints section

Behavioral rules for agents.
Fold in from existing CLAUDE.md if present, or ask the user.
Standard constraints include:
- Branch policy (feature branches, no direct commits to main/beta)
- File modification guards (which files need approval)
- Linear team and issue rules
- J1 rule (no implementation specs in markdown)
- Security constraints (API keys, secrets)

### ## Scope section (full template only)

Populate from Phase 0 grill answers.
Structure: ### In / Out / Uncertain table, ### Constraints, ### Resources.
Replace what SCOPE.md/SCOPE.json used to hold.

For priorities: add one line "See MAP-* issues for current priorities." instead of duplicating Linear content.

### ## Architecture section

Three required subsections:

**### Key design decisions:**
Flat bullet list. Each bullet: what was decided + why + where in code (file path or ADR reference).
This replaces ADR creation for simple decisions that don't warrant a full ADR file.
Reserve full ADRs (docs/decisions/) for decisions that are hard to reverse, surprising without context, or have real trade-offs requiring detailed rationale.

```markdown
### Key design decisions

- **Contract-first development:** Pydantic models define all API shapes. Generated OpenAPI spec consumed by frontend. Drift check in CI. See `contracts/openapi.json`.
- **Config chokepoint:** Only `globals.py` reads os.environ. All other modules import from globals.
```

**### Source layout:**
Annotated directory tree of the project's source structure.
Include brief comments explaining what each directory/file does.
Helps agents navigate without grep.

```markdown
### Source layout

\`\`\`
src/
  app/
    router/          # Vue Router config
    stores/          # Pinia stores
  entities/
    vessel/          # Vessel domain composables and types
    portfolio/       # Portfolio domain
  shared/
    api/             # API clients (apiFetch, engineFetch)
    ui/m/            # Design system components (M-prefixed)
  pages/             # Page-level view components
  widgets/           # Composite UI blocks (navbar, sidebar)
\`\`\`
```

**### Components and boundaries** (or ### Endpoints / API surface for lean):
Describe the system's components, how they interact, and trust boundaries.

For projects with an architecture rule catalogue: invoke `/grill-with-docs` for each decision area per the existing Phase 1 process.

### ## Conventions section (full template only, optional)

Naming patterns, file placement rules, required/prohibited patterns, imports, formatting.
Keep it short - one line per convention.
This section grows during vertical slice builds when real patterns emerge from actual code.

Omit for architecture-only projects (stateless APIs, CLIs) that don't need convention enforcement.
Convention mode triggers on ## Architecture alone - ## Conventions is optional.

### ## Deployment section (full template only)

Scaffold if the project has any delivery target beyond a local checkout.
Include the `waypoint:deploy` fenced block, environments table, promotion gates, prerequisites.
`/ship` reads ## Deployment in CLAUDE.md.
Without it, `/ship` fails loud.

### ## Product context section (full template only)

Personas, external connectors, endpoint routing (if applicable).
Populated from Phase 0 grill answers.
Replace what CONTEXT.md/CONTEXT.json used to hold.
Drop Linear-redundant content (priorities, deadline tables).

### ## Testing section

Testing philosophy, layers, framework, structural tests.
Store testing philosophy in CLAUDE.md frontmatter: `testing-philosophy: integration-first | tdd | structural-enforcement`.

Ask via AskUserQuestion:
**"What's your testing approach?"**
- **Integration-first (Recommended)** - test user workflows end-to-end, unit test complex logic only
- **TDD** - test-first for all features, high unit coverage
- **Structural enforcement** - automated convention checks, smoke tests, minimal unit tests

### ## References section

Pointers to remaining external docs:
- ADRs (docs/decisions/)
- Glossary (docs/_GLOSSARY.md)
- Architecture rule catalogue (if exists)
- Test registry (if exists)
- Contracts (contracts/)

## Architecture decisions

Three paths based on what exists.

### Path A - Architecture rule catalogue exists

When the project has an `architecture-rule-catalogue.md`:
1. Read the catalogue. Parse rule families, severity distribution.
2. Invoke `/grill-with-docs` for each family systematically.
3. Cross-reference against existing ADRs.
4. Produce consolidated decision-tree ADRs for complex decisions.
5. Simple decisions go into ### Key Design Decisions as bullet points (no ADR file).
6. For API-consuming projects: check for endpoint registries.

### Path B - No catalogue, moderate/large project

1. Offer to bootstrap a rule catalogue.
2. If accepted: seed rule families from the grill.
3. Then proceed as Path A.

### Path C - Small project, no catalogue

Fall back to the existing area catalog.
Simple decisions go into ### Key Design Decisions.
Complex decisions get ADR files in docs/decisions/.

## Convention enforcement scaffolding

Offer to create convention-enforcement tests.

Present via AskUserQuestion (multiSelect: true):
**"Which convention tests should I scaffold?"**
- **Structure tests (Recommended)** - verify file placement matches canonical taxonomy
- **Import tests** - no cross-domain imports, no circular dependencies
- **Auth coverage tests** - every route has authentication enforcement
- **None for now** - skip, add later via `/tdd`

## Hook scaffolding

Offer to configure `.claude/settings.json` with enforcement hooks.

Present via AskUserQuestion (multiSelect: true):
**"Which hooks do you want to set up?"**
- **Safety deny lists (Recommended)** - block destructive git operations and cloud CLI
- **CONCERNS.md injection** - loads unresolved concerns into every prompt
- **Doc-sync reminders** - reminds when docs need updating after file edits
- **Concurrent agent coordination** - claims tracker for multi-session work

## Documentation structure

After CLAUDE.md generation, create the minimal docs/ tree:

```
docs/
  _GLOSSARY.md               # Domain glossary
  decisions/                 # Architecture decision records (full ADRs only)
  _local/                    # Gitignored working state
    learnings/
    notes/
```

For migration projects, add `docs/program-legacy-{source}/`.

The Documentation Map is no longer a separate section - CLAUDE.md IS the documentation.
The ## References section in CLAUDE.md points to the remaining external docs (ADRs, glossary, catalogue, contracts).
